## 先看一眼发生了什么

开始修改前查看工作区状态，提交前再阅读一次差异，是成本很低却很有价值的习惯。

```bash
git status --short
git diff
git diff --staged
```

这三个命令分别帮助你确认改动范围、尚未暂存的内容和即将进入提交的内容。

## 一次提交只做一件事

如果修复导航链接时顺手重写了全部样式，未来回看这次提交就很难判断每行变更的目的。

可以先完成链接修复并验证，再把视觉调整放进下一次提交。小提交更容易审查，也更容易定位问题。

## 提交信息解释结果

比起「更新代码」，「修复移动端导航展开时的文字对比度」能告诉阅读者改动解决了什么问题。

提交正文可以补充触发条件与验证方式，不必复述差异中已经清楚可见的每一行代码。

## 给未来的自己留线索

好的提交记录像一本简短的开发日志。几个月以后，你不必重新猜测当时的上下文，就能理解这个决定。
